Part A Q4: Four Outputs per Thread

HPML Homework 3 | Matrix-multiply comparison | November 17, 2026 at 03:09 PM ET

The saved matmultKernel01.cu implementation was compiled as matmult01 and compared against the provided matmult00 at equal matrix dimensions. The ratio of median kernel times ranged from 0.98x to 1.68x. All 40 executions, including correctness smoke tests and warm-ups, passed the driver's CPU reference check. The saved kernel source was tested without changes.

Implementation and experimental setup

Both programs use 16 x 16 thread blocks. The baseline has a 16 x 16 footprint and one output per thread. The new kernel has a 32 x 32 footprint: thread (r,c) accumulates outputs at (r,c), (r,c+16), (r+16,c), and (r+16,c+16) within the output tile. Four scalar accumulators retain partial sums across reduction tiles. Each thread loads four A elements and four B elements into shared memory using the same quadrant mapping. A barrier precedes computation and another precedes tile reuse; the 32-step inner accumulation loop has a #pragma unroll directive.

The experiments ran on an NVIDIA GeForce RTX 4060 Laptop GPU (8188 MiB), Intel Core Ultra 9 185H CPU, and Ubuntu 24.04.1 LTS in WSL2 on Windows. The driver was 566.26. Both programs used CUDA nvcc 12.6.85, GCC 13.3.0, and -O3 -std=c++14 -arch=sm_89, with FOOTPRINT_SIZE defined as 16 or 32 as appropriate. Both were linked to the same unchanged driver and timer, using the shared CUDA runtime. CUDA_MODULE_LOADING=EAGER was set for both programs to match the controlled Q3 setup.

The argument is multiplied by each program's footprint. Passing the same argument to both programs would therefore compare different matrix dimensions. Each version was first checked at sides 32 and 96. Required sizes then received one excluded preliminary run per program, followed by five measured rounds. Size order and program order within each size were shuffled with seed 6998. Each invocation was a new process with one kernel launch; all measured trials were retained.

The unchanged driver uses deterministic FP32 matrices and compares every output against CPU matrix multiplication with absolute tolerance 0.01. Maximum observed absolute error was 0. Timings came from the supplied CUDA events with stop-event synchronization and exclude allocations, transfers, CPU reference computation, and cleanup.

Speedup is the ratio of medians from five runs per program and size. A value above 1 means matmult01 is faster. The baseline was rerun in this session; earlier Q3 data remains unchanged. These are kernel speedups, not full-process speedups.

Why the larger footprint changes performance

At a fixed load or store instruction, adjacent threadIdx.x values access consecutive columns. Each half-warp accesses 16 consecutive floats in one matrix row, producing aligned contiguous accesses for these dimensions. This preserves coalesced global-memory accesses while the larger footprint increases reuse. Each staged A or B value participates in 32 output multiply-accumulates within a block, compared with 16 in the baseline: a twofold increase in reuse.

For footprint F, each block loads 2F^2 floats per reduction tile, there are n/F reduction tiles, and (n/F)^2 output blocks. Thus total requested A/B loads are 2n^3/F floats. Increasing F from 16 to 32 halves these requested input loads. Output stores remain n^2 floats. This is a source-level access count, not measured DRAM traffic; cache behavior can change physical traffic. Ignoring output stores, work per byte loaded increases from about 4 to 8 FLOP/byte.

The tradeoffs are four accumulators per thread instead of one and 8 KiB of shared-memory tiles per block instead of 2 KiB. For equal n, matmult01 launches one quarter as many blocks, each with twice as many elements along the reduction tile and half as many reduction stages. Additional register and shared-memory use and the smaller block count can affect occupancy and scheduling, so a twofold reuse increase does not guarantee a twofold speedup. The inner-loop unroll directive is present in both versions; this experiment does not isolate an unrolling-only speedup.

At 256 x 256, the median changed from 0.442 to 0.453 ms: about 2.5% slower, with substantial run-to-run variation, so these measurements do not demonstrate a small-matrix benefit. At 512 and 1024, the median speedups were 1.32x and 1.68x. The 1024 baseline includes a 7.980 ms run; keeping it raises the ratio of means to 2.37x, versus the reported 1.68x ratio of medians. The slow run was retained, and its cause was not measured.

Using 2n^3 operations divided by median kernel time, throughput was 75.92, 366.21, 813.44 GFLOP/s for matmult00 and 74.07, 482.80, 1370.44 GFLOP/s for matmult01, in increasing size order. These are derived rates. No hardware-counter profiling was performed to establish exact occupancy or attribute the entire speedup to a single mechanism.
